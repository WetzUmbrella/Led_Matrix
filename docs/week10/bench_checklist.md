## Part B0: two-tile skew rig dry run from `b4/wire-w10` (no evidence)

Purpose: find wiring, WiFi, flashing and log problems before the evidence run. Nothing from B0 is committed as T-B4-03 evidence; the bench log notes that it was a dry run on `b4/wire-w10` and the hash flashed.

Hardware: 2 tiles, the Pico W, the router (same SSID for all three, AP isolation off), the logic analyser, 2 jumper wires per tile (test pin and GND), USB cables.

What the build does (from the code, not measured): the Pico joins the router and broadcasts BEACON {session_id 0, seq, t_p} to UDP 4210 every 100 ms (`coordinator_loop.c`), printing `BEACON seq= t_p= late_us=` per beacon and `LATE_HIST` every 100 beacons. Each tile joins the router, `tile_net` prints `TN_RX_HOOK 1` and then one `BCN,<seq>,<t_p>,<t_l>` line per beacon and `TN_STATS` every 100 beacons; `display_engine` prints `display_engine: test pin GPIO4, first tick <n>`, pulses GPIO4 on each 60 fps tick (1 ms, 4 ms when n mod 64 == 0), moves one LED (n mod 64) at value 8, and prints `DE ticks= missed=` periodically. The tile sends no HELLO, so the Pico prints no `JOIN` lines; that is expected in this build.

**Known start-up limit (logged as a defect for T-B5-01 and T-B4-04):** `display_engine` takes its first tick from the tile's own clock at boot, before any beacon. If a tile booted before the Pico, its first deadline lies in the future by about the difference in uptime and the pin stays low that long. Always power the Pico first, wait for its `BEACON` lines, then reset the tiles. If the Pico is reset during the run, reset both tiles afterwards.
